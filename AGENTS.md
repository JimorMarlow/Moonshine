# Moonshine — инструкции для агентов

Контроллер ректификационной колонны на ESP32 (WROOM-38U): температура DS18B20,
датчики потока Холла, веб-интерфейс (страница в PROGMEM), настройки в LittleFS.
Прошивка на PlatformIO + Arduino framework.

## Сборка и проверка

`pio` не в PATH — вызывай полный путь:

```powershell
& "$env:USERPROFILE\.platformio\penv\Scripts\pio.exe" run -e esp32-wroom-38u
```

- Перед тем как сказать «готово», собери проект этой командой и покажи итог (RAM/Flash, ошибки).
- Ошибки компиляции читай из вывода целиком: сначала первая ошибка, остальные часто её следствие.
- Прошивка и монитор требуют подключённой платы — **спроси пользователя**, прежде чем заливать:

```powershell
& "$env:USERPROFILE\.platformio\penv\Scripts\pio.exe" run -e esp32-wroom-38u -t upload
& "$env:USERPROFILE\.platformio\penv\Scripts\pio.exe" device monitor -b 115200
```

- Полная очистка: `... pio run -t clean`. Не чисти `.pio` без причины — сборка станет дольше.
- Юнит-тестов в проекте нет; критерий корректности — успешная сборка плюс проверка логики чтением кода.

## Что важно не сломать

- `src/pinout.h` — фактические назначения пинов. Не меняй их без явного подтверждения пользователя.
- `platformio.ini` — зависимости зафиксированы (ETL, Gyver-библиотеки, LiquidCrystal_I2C).
  Новую библиотеку добавляй только по просьбе; версии не поднимай «заодно».
- `src/version.h` — версия прошивки; `sync_version.py` при сборке подставляет её в `package.json`.
  Поднимай PATCH при обычных правках, MINOR — при новых возможностях.
- Веб-интерфейс (`src/web-ui.cpp`): HTML-страница лежит в PROGMEM (`HTML_PAGE`), большие строки
  держи в PROGMEM, следи за свободной RAM (сборка печатает её в конце).
- Строки интерфейса и сообщения — на русском, как в существующем коде.
- Ничего не выкладывай в git самостоятельно, после завершения этапа разработки, если я попросил
  увеличить версию, подготовь текст с описанием коммита, покажи мне, я сам выложу после коррекции.

## Веб-интерфейс и режим настройки (как реализовано)

Два сервера на базовых классах ETL (`etl::webui`):

- **сервер контента** (`webui::moonshine_web_server`) — обычный режим: страница мониторинга и JSON;
- **сервер настроек** (`etl::webui::server_setup`) — сеть, тема, шрифт; создаётся на время настройки
  и уничтожается при возврате, память постоянно не занимает.

Переключением управляет `webui::moonshine_web_manager` (`etl::webui::web_manager`): методы
`start_content()` / `start_settings()` останавливают текущий сервер и запускают новый,
`on_create_content()` / `on_create_settings()` его создают.

1. Вход в настройки — `/api/settings` (кнопка ⚙), три клика аппаратной кнопкой или удержание кнопки
   при старте. Обработчик только планирует callback (`schedule_settings_cb()`), наш callback
   выставляет флаг, а само переключение делает `handle_pending_switch()` из `loop()`: останавливать
   сервер внутри его же HTTP-обработчика нельзя.
2. `start_settings()` вызывает у старого сервера `stop()`, а базовый `web_server_base_t::stop()`
   делает `MDNS.end()`, останавливает HTTP-сервер, затем `WiFi.disconnect(true)`,
   `WiFi.softAPdisconnect(true)` и `WiFi.mode(WIFI_OFF)` — **Wi-Fi выключается**. Новый сервер
   в `begin()` поднимает его заново: пустой `wifi_ssid` → сразу `Moonshine_AP`, непустой → до 10 с
   попытка подключиться к локальной сети, при неудаче AP. Поэтому при переходе в настройки точка
   доступа перезапускается (тот же SSID, обрыв 1–2 с; до 10 с, если сохранённая сеть недоступна),
   а не остаётся непрерывной.
3. Страница перехода на настройки не делает одиночный редирект: она опрашивает `/` каждые 2 с,
   пока новый сервер не ответит.
4. WiFi-менеджер ETL один на всё время работы (`set_wifi_manager()`). Если каждый сервер создаёт
   свой, деструктор старого сервера вызывает `manager::~manager()` → `stop()` → `WiFi.mode(WIFI_OFF)`
   уже после старта нового и гасит его точку доступа.
5. Возврат без сохранения — `/api/back`: на ESP32 планируется callback контента и менеджер
   переключается обратно тем же механизмом (Wi-Fi снова перезапускается); на ESP8266 библиотека
   вместо этого перезагружает контроллер.
6. Сохранение — `/api/save`: в LittleFS пишутся настройки Wi-Fi (`/settings/wifi.cfg`) и интерфейса
   (`/settings/ui.cfg`), клиенту уходит ответ, затем `ESP.restart()`. `/api/reset` сбрасывает
   настройки к значениям по умолчанию и тоже перезагружает.
7. После перезагрузки `setup()` вызывает `start_web_ui(кнопка зажата)`: настройки читаются из
   LittleFS и поднимается сервер настроек (кнопка зажата) либо web-ui. Далее `manager::begin()`:
   непустой `wifi_ssid` → подключение к локальной сети, при успехе `WiFi.mode(WIFI_AP_STA)`,
   но `softAP()` не вызывается — точки доступа нет, доступ только по адресу в локальной сети;
   иначе — режим AP.
8. mDNS `moonshine.local` поднимается и в AP, и в STA; сервис `http` регистрирует сам WiFi-менеджер,
   нашим серверам его добавлять не нужно.

Если понадобится, чтобы AP при переключении не прерывалась вообще, нужно переопределить `stop()`
в обоих серверах: гасить только HTTP-сервер и mDNS, не трогая Wi-Fi.

## Стиль

- Не переформатируй чужие файлы целиком: минимальный diff, тот же стиль, те же имена.
- Комментарии — по делу и на русском; не комментируй очевидное.
- Не трогай `.pio/`, `docs/`, `README.md` без необходимости.
- Коммиты короткие, на русском, в стиле истории (`v1.2.13 исправлен опрос DS18B20`).

## Порядок работы

1. Сначала прочитай затронутые файлы (и `README.md`), потом правь.
2. Меняй по одной логической вещи за раз, после каждой — сборка.
3. Для поиска по коду и проверки чужих правок используй сабагентов, но правки делай сам.
4. Если сборка падает по причине окружения (нет тулчейна, нет платы) — скажи об этом прямо,
   не выдавай это за ошибку кода.
